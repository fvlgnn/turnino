# Administration

Turnino has one installation administrator and deliberately avoids accounts, roles and external identity services. Administrator access uses a random access key generated by Turnino. Only its SHA-256 hash is stored in SQLite, and the clear-text key is shown once.

## First setup

Stop Turnino before running maintenance commands against its database.

For a native installation:

```sh
make build
./bin/turnino admin init --data-dir ./data
make dev
```

For Docker Compose:

```sh
docker compose run --rm turnino admin init --data-dir /data
docker compose up -d
```

Copy the generated access key into a password manager, then use it at `/admin`. Running `admin init` again is safe: it refuses to replace an existing key.

## Rotate the access key

Open **Administration security** near the bottom of the administration page, confirm the operation and generate a new key.

Rotation immediately invalidates the old key and every active administrator session. The new key is shown once; save it before leaving the result page, then sign in again.

## Offline recovery

If the key is lost, stop Turnino and explicitly reset it:

```sh
./bin/turnino admin reset --data-dir ./data --confirm
```

With Docker Compose:

```sh
docker compose stop turnino
docker compose run --rm turnino admin reset --data-dir /data --confirm
docker compose up -d
```

The `--confirm` flag is an explicit acknowledgement that the reset invalidates the current key. `--apply` is not used because the command has no preview or `--dry-run` mode: without `--confirm`, it makes no changes. The command generates a replacement key and invalidates the previous one. Existing browser sessions are stored in memory and disappear when the stopped server exits.

## Advanced automated bootstrap

`TURNINO_ADMIN_TOKEN` remains available for unattended and automated deployments. Set a random value of at least 20 characters only when starting a new database:

```sh
TURNINO_ADMIN_TOKEN="$(openssl rand -base64 32)" ./bin/turnino
```

Turnino stores only its hash. After the first successful startup, remove the variable from the runtime environment and retain the value in a secret manager. A later environment value cannot silently overwrite the stored key; use the UI rotation or the explicit offline reset instead.

Environment variables are convenient but may be visible to process-inspection, deployment and diagnostic tools. For persistent deployments, inject the value through the platform's secret-management mechanism where possible.

## HTTP, HTTPS and deployment responsibility

Plain HTTP does not encrypt traffic. On an untrusted network, an observer may intercept the administrator access key during login, the session cookie, counter keys or operational data. HTTP is acceptable only when the deployment owner has deliberately chosen a trusted and isolated network.

For any installation exposed beyond such a network, terminate HTTPS at a properly configured reverse proxy, redirect or block plaintext HTTP, and keep Turnino's backend port inaccessible to untrusted clients.

Turnino controls application authentication, authorization, CSRF protection and credential storage. It cannot configure the host firewall, router, VLAN, Wi-Fi isolation, DNS, TLS certificates or reverse proxy. A deployment that exposes plaintext HTTP is therefore an infrastructure security decision, not a failure of Turnino's authentication logic. The person operating the installation remains responsible for securing that network path.

Turnino's embedded listener currently serves HTTP. A reverse proxy should therefore expose only its HTTPS listener to clients, redirect or disable its HTTP listener, and keep Turnino's plaintext backend private.
